# Internationalization (i18n) design

**Date:** 2026-10-19
**Status:** Implemented; awaiting review
**Outcome:** The web UI, public pages, HTTP API errors, widget output, and bot chat replies can be shown in English or Simplified Chinese, with a visitor-controlled language switch and a structure that accepts more languages later.

## Intent

TS6 Manager is an open-source project used by TeamSpeak communities in many countries. Today every user-facing string is hardcoded English. Visitors should be able to read the interface in their own language without an administrator changing a deployment setting, and server operators should be able to choose the language their music/video bots speak in TeamSpeak chat.

## Goals

1. Ship English (`en`) and Simplified Chinese (`zh-CN`) for the entire web interface, including authenticated pages, login/setup, public widget pages, and Listener Remote.
2. Let each visitor switch language at any time. The choice persists locally; first visit follows the browser language with English fallback.
3. Localize HTTP API error responses from `Accept-Language`; keep response shapes and stable `reason` codes unchanged.
4. Localize bot chat replies per bot, with an instance-wide default.
5. Keep adding a third language a matter of adding one locale directory (plus bot/backend messages where applicable).
6. Keep existing English API strings, Playwright selectors, and screenshot fixtures stable by making `en` the default and preserving current English wording.

## Non-goals

- Translating the documentation site (`docs/public/`) or README/CHANGELOG.
- Translating server logs written by the backend, audit/activity rows stored in SQLite, or Docker image metadata.
- Translating user-generated or TeamSpeak-supplied content: server/channel/client names, bot nicknames, custom commands, flow messages, playlist titles, TeamSpeak error text.
- A translation management platform (Crowdin/Weblate). Locale files are laid out so one can be added later.
- Localizing the PWA manifest name/brand; "TS6 Manager" stays the product name.
- Auto-following OS language changes while the tab is open.

## Anti-goals

- Do not store translated display text in the database. Store stable codes/keys and render translations at request/render time.
- Do not build sentences by concatenating translated fragments across locales; use complete sentences with `{{placeholders}}`.
- Do not use English text as a translation key.
- Do not break API tests or third-party clients that read `error`/`details`: English output stays byte-identical when the negotiated locale is `en`.
- Do not require an account or admin rights to change the interface language.

## Decisions from the conversation

| Decision | Value |
|---|---|
| Audience | Open-source visitors; per-visitor switching |
| Launch languages | English (source/fallback) + Simplified Chinese |
| Backend errors | Localized server-side from `Accept-Language` |
| Logs | English |
| Public widget | Follows visitor language |
| Docs site | Out of scope |
| Bot chat replies | In scope, per-bot language with instance default (builder call) |

## Builder-check decisions

These were raised by the independent design review and settled by the builder (the user delegated open choices):

1. **Backend prose in successful responses is in scope.** Connection diagnostics, media diagnostics, and similar strings generated per request are localized server-side from `Accept-Language`. Responses generated once and stored (for example a video stream's `lastStop` detail) instead gain stable codes/params and are translated in the frontend, so a later language change is still correct. `LanguageSync` invalidates TanStack Query caches when the language changes so cached diagnostics refetch in the new language.
2. **Stable error identity may be added.** Existing `error`/`details` values stay byte-identical for `en`, but adding `reason`/`code` fields is allowed. Frontend classifiers move from English substring matching to `reason` first, with text matching only as a backward-compatible fallback.
3. **Widget and BBCode output are in scope.** `?lang=` is accepted and validated on every public widget endpoint (`data`, SVG, PNG, player BBCode) and overrides `Accept-Language`. Generated embed snippets include the active UI locale. Player BBCode defaults to the bot's configured language when no `?lang=` is given.
4. **Translation quality gate is builder-authored zh-CN.** No native reviewer is available in this session; translations are reviewed for terminology consistency (频道/客户端/查询/机器人), key parity, and placeholder parity. A native review can happen before release without changing the structure.
5. **Server-rendered widget text needs CJK glyphs.** Add a Noto CJK font package to the backend runtime stages (`Dockerfile.backend`, `Dockerfile.all-in-one`) and verify SVG/PNG output; record the image-size impact in the PR.

## Technical design

### Locale model

```ts
type SupportedLocale = 'en' | 'zh-CN';
type LanguagePreference = 'system' | SupportedLocale;
```

- Fallback locale: `en`.
- `zh`, `zh-Hans`, `zh-CN`, `zh-SG`, `zh-MY` normalize to `zh-CN`; any `en-*` normalizes to `en`; unknown tags resolve to `en`.
- Negotiation (server and client) parses `Accept-Language` with q-values, ignores `q=0`, and picks the highest-weighted supported match.

### Frontend

Add `i18next` + `react-i18next`. No language-detector plugin: the app already owns persistence in `ui.store`, and a small resolver is easier to test.

```
packages/frontend/src/i18n/
  index.ts              # init, changeLanguage, document.lang, title helpers
  languages.ts          # supported locales, normalize, systemLanguage, Accept-Language parsing
  locales/en/<ns>.json
  locales/zh-CN/<ns>.json
```

Namespaces (split for maintainability, loaded statically):

| Namespace | Contents |
|---|---|
| `common` | shared actions, states, errors, units, table/dialog defaults |
| `app` | shell, sidebar, page titles, dashboard, auth/login/setup |
| `admin` | servers, channels, clients, groups, permissions, bans, tokens, files, complaints, messages, logs, audit, activity journal, instance, diagnostics |
| `settings` | Settings tabs, forms, appearance, users, YouTube, about |
| `media` | media bots, library, playlists, requests, radio, IPTV, bot hub/console |
| `bots` | flow editor, node types, templates, bot editor |
| `public` | widget page, Listener Remote, language menu |
| `content` | long-form help: connection setup, TeamSpeak docs, bot templates copy |

Key convention: `<area>.<component>.<meaning>` (e.g. `media.queue.addButton`, `common.action.save`). Plurals use i18next suffixes (`_one`, `_other`); Chinese uses `_other`. Rich text with embedded links uses `<Trans>`; everything else uses `t()`. Dates/numbers use `Intl` and `date-fns` locale objects driven by `i18n.language`.

Language state:

- `ui.store` gains `language: LanguagePreference`, default `'system'`; persist version bumps and migration preserves existing users.
- A `LanguageSync` component (mounted once in `App`) reads the store and calls `i18n.changeLanguage`, updates `document.documentElement.lang`, and updates `document.title` keys.
- `main.tsx` initializes i18n synchronously from the persisted preference (read the same localStorage entry before React renders) to avoid a flash of English.
- `api/client.ts` request interceptor sends `Accept-Language: <resolved locale>` on every API call.

Switcher UX:

- Settings → Appearance gains a **Language** section: System default / English / 简体中文, with the resolved language shown.
- Public surfaces (login, setup, `/widget/:token`, `/remote`) show a compact globe menu in the corner using the same store.
- Widget embedders can pass `?lang=en|zh-CN` to override the language for that widget without changing the visitor's stored preference.

String conversion:

- Convert every user-visible literal in `src/**` page by page: JSX text, `placeholder`, `title`, `aria-label`, `alt`, toast/error strings, empty states, confirm dialogs, table headers, validation messages, page titles.
- Refactor label constants to keys where they are data today: `src/data/bot-templates.ts`, `src/content/connection-setup.ts`, `src/content/teamspeak-docs.ts`, sidebar sections, permission Simple labels, media command labels, flow node types.
- Keep CSS classes, API paths, enum values, and test ids untouched.
- Any interpolation uses named placeholders; no template strings assembled from translated pieces.

### Backend

Small custom module (no i18next dependency in the Node image):

```
packages/backend/src/i18n/
  index.ts        # negotiateLocale, t(locale, key, vars), resolveBotLocale
  locales/en.ts
  locales/zh-CN.ts
  i18n.test.ts    # parity, negotiation, interpolation
```

- Express middleware resolves `req.locale` from `Accept-Language`, defaults to `en`, and sets `Content-Language`. Add `Vary: Accept-Language` to cacheable responses (widget SVG/JSON, channel banners).
- `AppError` gains a message key + params; `message` remains English for logs/stack traces. The error handler emits localized `error`/`details` while keeping `reason`, `retryable`, and status codes unchanged.
- Route-level ad-hoc `res.json({ error: '…' })` responses are converted to the shared error helper (or `AppError`) so their text comes from the dictionary. `en` values must equal today's strings.
- Dynamic upstream text (TeamSpeak errors, yt-dlp/FFmpeg output, network errors) is interpolated into a localized sentence, not translated.
- No `Accept-Language`: `en` (preserves tests and API clients).

### Bot chat

- `MusicBot.language String?` (`null` = inherit). New `AppSetting` key `default_bot_language`, default `en`. Bump `packages/backend/prisma/SCHEMA_VERSION`.
- `resolveBotLocale(bot, defaultSetting)` picks the bot language, then the instance default, then `en`.
- Backend bot-chat namespace covers `!help` blurbs, Now Playing, queue/playlist/history output, playback errors, and automation notices. It is separate from HTTP API messages because bot replies have no request context.
- API validation accepts `language: null | 'en' | 'zh-CN'`; the media-bot create/edit form gets a Language select (Default / English / 简体中文). The instance default is editable in Settings → Appearance under the language section.
- Existing English bot replies stay identical in the `en` dictionary.

### Widget output

- Server-rendered SVG labels (e.g. `ONLINE`, generated stats labels) use the negotiated locale; user-configured spacer text and server/channel/client names are untouched.
- Add `Vary: Accept-Language` wherever widget or banner responses are cacheable.
- Widget JSON API localized fields (if any) use the same middleware; otherwise the React widget page handles its own text.

### Tests and CI

- Frontend unit tests: language normalization/negotiation, store migration, interpolation/plural behavior, locale key parity across all namespaces (same keys, same placeholders, non-empty values).
- Backend unit tests: negotiation, interpolation, `en` output byte-identical to current strings for representative errors, bot locale resolution, bot chat formatting in both locales.
- Existing route tests keep asserting English because the default locale is `en`.
- Playwright: `use.locale = 'en-US'` in `playwright.config.ts` so current specs stay deterministic; new `i18n.spec.ts` switches to 简体中文, checks nav/dashboard/settings, reloads to confirm persistence, then switches back.
- Docs screenshot fixture forces `en` so maintained screenshots stay stable.
- Optional repo-hygiene check: `scripts/ci/check-i18n.py` validates frontend JSON (key parity, placeholders, empty values, duplicate keys). Backend `.ts` dictionaries are covered by `i18n.test.ts`.

## Implementation order

1. **Scaffolding**: dependencies, i18n init, language store + migration, switcher in Settings and public pages, axios header, key-parity tests, Playwright locale pin, backend negotiation middleware/helper + error handler plumbing.
2. **Shell and public surfaces**: layout/sidebar/nav, login/setup, dashboard, shared components, empty/error states, page titles.
3. **Admin surfaces**: servers, channels, clients, groups, permissions, bans, tokens, files, complaints, messages, logs, audit, activity journal, instance, diagnostics.
4. **Media and bots**: media bots, library, playlists, requests, radio, IPTV, bot hub/console, flow editor/templates, long-form help content.
5. **Backend messages**: convert route errors and `AppError` sites to keys; widget SVG; bot chat + Prisma field/UI; default bot language setting.
6. **Sweep**: grep for remaining hardcoded user-visible strings, run typecheck/build/unit/Playwright/Go, responsive check with Chinese text, screenshot check.

Each phase must leave `pnpm typecheck`, `pnpm build`, frontend/backend tests, and Playwright green. Untranslated pages remain English until their phase lands; English stays the default, so intermediate states are shippable.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Large diff / merge conflicts | Phase commits; convert one page/namespace at a time |
| Translation drift and missing keys | Key-parity test in CI; localized fallback to `en` at runtime |
| Chinese text overflow breaks layouts | Responsive/fixture review at 1366×768 and narrow widths; allow wrapping, avoid fixed widths |
| Existing tests assert English text | Keep `en` as default; pin Playwright `locale`; preserve English wording |
| Localized cache leaks across languages | `Vary: Accept-Language` on cacheable public responses |
| Stored audit text becomes stale | Keep structured `action`/`outcome`/`resultCode`; localize labels in the frontend |
| Backend error refactor changes behavior | Keep status/reason/retryable; add tests comparing `en` output to current strings |
| Bot chat has no request language | Explicit per-bot setting + instance default; never infer from a TeamSpeak client |
